01 / 05

Solo — desktop only, one device

Everything on one machine, bound to loopback. Nothing crosses the network. Today's codebase requires the server to run locally for login, even though there's no one else to sync with.

Build & packaging

  • New: apps/server/Dockerfile + docker-compose.prod.yml — neither exists yet.
  • Desktop build: no NEXT_PUBLIC_API_URL override needed — http://localhost:8787 is already the default and already CSP-allowed.
  • pnpm --filter @boardly/web build && pnpm --filter @boardly/desktop tauri:build
  • Back up the Postgres volume before restarting the server with new code — migrations run automatically on boot.
02 / 05

Solo — your own multiple devices

One server becomes the shared source of truth; every device reaches it over a real network. The desktop CSP already allows https:/wss: to any host — only plain http/ws is locked to localhost — so a TLS-fronted server is a build-time env change, not a code change.

Env changes vs. sheet 01

VarValueWhere
HOST0.0.0.0server — Caddy/Tailscale must reach it
CORS_ORIGINShttps://tauri.localhostserver — unchanged, all devices run desktop
NEXT_PUBLIC_API_URLhttps://your-name.ts.netweb build, baked in before tauri:build

Notes

  • Recommended path: Tailscale Serve/Funnel on the box running the server — real HTTPS cert, zero public exposure, zero manual TLS.
  • Alternative: small VPS + Caddy for automatic Let's Encrypt.
  • Rebuild once with the new NEXT_PUBLIC_API_URL — the same installer goes on every device.
03 / 05

Desktop + Web, same person

Adds a browser client alongside desktop. The web build serves as a static export from anywhere; the browser talks to the same server desktop uses. Auth diverges here — web uses an httpOnly cookie, desktop uses the OS keychain — so same-site hosting keeps the cookie path simple.

Env changes vs. sheet 02

VarValue
CORS_ORIGINShttps://tauri.localhost,https://boardly.yourdomain.com
NEXT_PUBLIC_API_URLhttps://api.yourdomain.com (web build)

Notes

  • Deploy apps/web/out to Vercel/Cloudflare Pages/Netlify, or serve it as static files from the same box via Caddy.
  • Keep web and API on subdomains of one domain — avoids cross-domain cookie SameSite/Secure edge cases entirely.
04 / 05

Distributed to a few people, independent

Every recipient gets sheet 01's recipe and runs their own stack. No shared server, no shared env, no dependency between the boxes below — and no one but each person owns their own uptime or backups.

What you hand over

  • The repo + sheet 01's docker-compose.prod.yml / .env.production template.
  • Before anyone else installs it: change identifier in tauri.conf.json off the placeholder vn.moonbase.boardly.

The alternative, and why sheet 04 isn't it

You could host one server and give everyone accounts on it — the auth/signup system already supports multiple users. That's a real commitment (sheet 05, not this one): you'd own their data durability, not just your own.

05 / 05

Commercial — hosted, many users, each on multiple devices

Now you own the uptime. Every user's own devices sync through infrastructure you run for all of them at once — which means the single in-memory server from sheets 01–04 becomes the bottleneck. This sheet is deliberately the busiest: it's the one where complexity is real, not decorative.

What's a real gap today, not a config flip

  • GAP@hocuspocus/extension-database is the only extension wired (apps/server/package.json) — there's no cross-instance pub/sub. Two users on different server instances in the same room won't see each other's edits live until reconnect. Needs a Redis (or equivalent) extension before running >1 instance.
  • GAP the updater's signing key was deliberately discarded per docs/units/UNIT-5.2-tauri-plugins.md — a real release pipeline needs a real keypair.
  • GAP identifier is still the placeholder vn.moonbase.boardly; commercial distribution needs a real bundle id plus macOS notarization / Windows code signing.
  • Auth/signup multi-tenancy itself already works — this sheet is infrastructure scale-out, not a data-model change.
